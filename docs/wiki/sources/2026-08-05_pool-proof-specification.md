## Summary

The approved build phase makes an executable Pool Proof the next bounded step before further supervisor governance. It separates:

- a reusable **Minimal Pool Runtime** that queues direct jobs, allocates ready slots, launches fresh headless Pi Workers, persists minimal truthful results, and contains one Worker failure; and
- a **Pool Proof Harness** that owns the deterministic fixture, controlled fault injection, independent verifier, and proof report without simulating the pool.

The candidate is a two-node vertical DAG:

1. `single-worker-pool-proof`
2. `multi-worker-pool-proof`

The fixture repository is required. An `agent-pool` dogfood task is the first follow-up, not a proof completion criterion.

## Identity and safety boundary

A Repository Builder builds the environment in which Pool Workers operate; it does not become a Worker. The trusted launcher establishes Worker identity structurally through isolated Pi configuration/session paths, immutable attempt context, mutually exclusive resources, workspace-confined tools, and runner-owned result identity.

The trusted credential-bearing Pi control process is separated from untrusted repository commands, which run in a non-root, resource-bounded per-attempt sandbox with no provider or GitHub credentials. The proof remains fixture-only and explicitly does not claim full production audit or arbitrary-repository readiness.

## Explicit deferrals

The approved phase defers free-form decomposition and Gate 1, Graphify/predicted-touch scheduling, full DAG failure and recovery policy, Tier-2 evaluation, full CRAFTS/history activation, builder calibration, integration/GitHub delivery and webhooks, and full backup/restore/operational audit work.
